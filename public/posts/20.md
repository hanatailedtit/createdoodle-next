# [C++] RTSP 실시간 웹 스트리밍 서버 구축기

## 1:N 브로드캐스팅과 세션 격리를 통한 저지연 스트리밍 설계

특수 장비 제어를 위한 웹 GUI를 개발하는 과정에서, 가장 핵심적인 요구사항은 다수의 사용자가 지연 없이 실시간 CCTV 영상을 확인할 수 있는 환경을 구축하는 것이었습니다.

단순히 RTSP 스트림을 재생하는 수준을 넘어, 다중 접속 환경에서도 안정적으로 동작하는 스트리밍 아키텍처가 필요했습니다.

이 글에서는 C++ 기반 백엔드에서 RTSP 스트림을 WebSocket으로 중계하는 서버를 직접 구현하면서 겪었던 지연 문제, 자원 병목, 세션 충돌 이슈와 이를 해결하기 위한 구조 개선 과정을 정리했습니다.

## 1. 전체 파이프라인 구성

웹 브라우저는 RTSP 프로토콜을 직접 지원하지 않기 때문에, 중간에서 스트림을 변환하고 전달하는 서버 계층이 필요합니다.

구성은 다음과 같습니다.

- RTSP Input: 장비에서 송출되는 CCTV 스트림
- FFmpeg: RTSP 스트림 디코딩 및 변환
- WebSocket Server (C++): 변환된 데이터를 브라우저로 전달

초기에는 Base64 인코딩을 고려했지만, 실시간 스트리밍 특성상 인코딩/디코딩 오버헤드가 부담이 되어 최종적으로는 바이너리(ArrayBuffer) 기반 전송 방식을 선택했습니다.

## 2. 백엔드 구조 설계

스트림 처리와 네트워크 송출을 분리하기 위해 다음과 같은 구조로 설계했습니다.

1. StreamWorker

- FFmpeg 프로세스를 실행
- 별도 스레드에서 출력 스트림을 지속적으로 읽음
- 읽어온 데이터를 내부 버퍼로 전달

2. StreamListener

- StreamWorker로부터 데이터를 수신
- 웹소켓을 통해 클라이언트로 전송

이 구조는 역할 분리가 명확해 구현은 수월했지만, 실제 운영 환경에서는 예상하지 못한 문제가 발생했습니다.

## 3. 문제 1: 스트리밍 지연(Latency)

초기 구현에서 가장 먼저 마주한 문제는 비정상적인 지연이었습니다.

서버는 정상적으로 데이터를 수신하고 있었지만, 브라우저에서는 몇 초 단위로 밀린 영상이 출력되었습니다.

### 원인

popen으로 실행한 FFmpeg 프로세스의 출력이 C 런타임의 Full Buffering 정책에 의해 지연되고 있었습니다.

즉, 데이터가 일정 크기 이상 쌓일 때까지 외부로 전달되지 않는 구조였습니다.

### 해결 방법

우선 etvbuf를 통해 버퍼링을 제거했습니다. (Unbuffered 모드)  
그 다음으로 \_read 기반으로 즉시 데이터 읽기 처리를 진행하였고, 세션 종료 시 pclose를 통한 명시적 자원 해제를 진행하였습니다.

### 결과

스트리밍 지연이 눈에 띄게 감소하였고, 장기 실행 시 발생하던 좀비 프로세스 문제도 해결되었습니다.

이 단계에서 실시간에 가까운 응답성을 확보할 수 있었습니다.

## 4. 문제 2: 다중 접속 시 자원 막힘

초기 구조는 다음과 같은 형태였습니다.

- 클라이언트 1명당 FFmpeg 프로세스 1개 생성

단일 사용자 환경에서는 문제가 없었지만, 여러 사용자가 동시에 접속하거나 브라우저 탭을 여러 개 열 경우 CPU 사용량과 네트워크 트래픽이 급격히 증가했습니다.

실제로 일정 수준 이상의 동시 접속에서 서버 전체가 불안정해지는 현상이 발생했습니다.

## 5. 해결: 1:N 브로드캐스팅 아키텍처

이 문제를 해결하기 위해 구조를 다음과 같이 변경했습니다.

### 핵심 전략

- 카메라 1대당 FFmpeg 프로세스는 1개만 유지하기로 하였습니다.
- StreamManager 도입
  - RTSP URL을 기준으로 StreamWorker를 관리하였습니다.
  - 동일한 스트림 요청 시 기존 Worker는 재사용하도록 로직을 작성하였습니다.
- StreamWorker 확장
  - 단일 스트림 데이터를 여러 클라이언트에 동시에 전송하도록 코드를 작성하였습니다.

### 처리 흐름

1. 클라이언트 요청 수신
2. 기존 스트림 존재 여부 확인
3. 존재 시 → 구독자 목록에 추가
4. 미존재 시 → 새로운 StreamWorker 생성
5. 단일 스트림 데이터를 모든 구독자에게 브로드캐스팅

### 결과

- CPU 사용량 급감하였습니다.
- 네트워크 효율성이 개선되었습니다.
- 동시 접속자 증가에도 안정적인 성능을 유지할 수 있었습니다.

구조 변경 이후, 부하 테스트에서도 안정적으로 동작하는 것을 확인할 수 있었습니다.

## 6. 문제 3: 세션 충돌 및 화면 혼합

다중 브라우저 창 환경에서 예상치 못한 문제가 발생했습니다.

- 서로 다른 창이 동일 세션으로 인식되었습니다.
- 특정 창의 요청이 다른 창에 영향을 주었습니다.
- 영상이 섞이거나 스트림이 전환되는 현상이 발생하였습니다.

## 7. 해결: 세션 격리(Session Isolation)

문제의 원인은 세션 식별 방식이었습니다.

기존에는 단순 숫자 생성 기반 세션 ID를 사용했는데,
이 방식은 클라이언트 구분이 명확하지 않았습니다.

### 개선 방법

- 각 스트림 요청에 대해 Instance ID를 부여하였습니다.
- WebSocket 객체와 Instance ID를 1:1로 매핑하였습니다.
- 요청을 보낸 동일 WebSocket으로만 응답을 전달하도록 하였습니다.

### 결과

- 창 간 간섭을 완전히 제거할 수 있었습니다.
- 스트림 혼합 현상을 해결할 수 있었습니다.
- 다중 창 환경에서도 안정적인 독립 스트리밍이 보장되었습니다.

## 마무리

이번 구현을 통해 단순 스트리밍 서버 이상의 문제를 다루게 되었습니다.

- OS 레벨 버퍼링 제어
- 프로세스 생명주기 관리
- 멀티스레드 동기화
- 세션 단위 라우팅

<br>
  
특히 인상적이었던 점은, 실시간 스트리밍 시스템은 특정 계층 하나만 최적화해서는 해결되지 않는다는 것이었습니다.

데이터 처리, 네트워크 전송, 클라이언트 관리까지 모든 요소가 균형 있게 설계되어야 안정적인 결과를 얻을 수 있다는 것을 깨달았습니다.
